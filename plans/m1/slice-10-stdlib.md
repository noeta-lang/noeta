# Slice M1.10 — Layered stdlib (Ring 1 + Ring 2)

Status: **in progress** (M1.10.1 Ring 1 string surface done; M1.10.2 list/map/set + M1.10.3 Ring 2 remaining)

## Goal
Ship the always-present standard library: rich Ring 1 core types entangled with the operator traits, and the thin Ring 2 always-shipped modules.

## Architecture (decided)

`lang-stdlib` is the home of the standard library. Its load-bearing idea: **where a Ring 1 operation is expressible over data represented *identically* in both runtimes, its semantics live in `lang-stdlib` once and both backends call into it — so the differential oracle holds by construction, not merely by test.** Strings are the canonical case: the M0 tree-walker (`Value::Str(String)`) and the M1 VM (`Payload::Str(String)`) both store a Rust `String`, so the entire string-method surface (behavior + arity + argument typing) is defined in `lang-stdlib` and each backend is reduced to thin value↔primitive glue (`Arg`/`Output`/`Dispatch`). Collection methods (list/map) manipulate backend-specific value representations and so are implemented per backend, with the differential as the guard.

Dispatch reuses the existing built-in-method site in both backends (the one that already handles `count`/`enumerate`) — **no compiler or bytecode changes**: a method call is already lowered generically and resolved at runtime.

## M1.10.1 — done (Ring 1 string surface)

No `unsafe` added.
- [x] **Conformance:** `strings/methods.lang` (every method, incl. ## Scope
- In:
  - **`lang-stdlib`** crate.
  - **Ring 1** (always present): `List`, `Map`, `Set`, ordered/sorted maps+sets, deque/queue; full Unicode-correct strings; numeric primitives; `Option`/`Result`. A Python-generous method surface (map/filter/fold, slicing, iteration, full string ops) bound to the M1.8 operator traits.
  - **Ring 2** (always shipped, thin): file/IO + filesystem (paths/streams); process/environment/args; basic scalar math; basic **seeded** random (general-purpose PRNG); basic time (now/sleep/measure/**monotonic** — no timezone/calendar); JSON.
- Out: Ring 3 (regex, crypto, HTTP client, timezone date/time, YAML/TOML/CSV, compression, 3D/SIMD math, derive-driven Serialize/Deserialize) — all post-M1 via the extension mechanism; async-first IO internals (M2).

## M1.10.2 — in progress (Ring 1 list/map)
- [x] **List `reverse`/`contains`/`join` + map `keys`/`values`/`has`.** Value-specific, so implemented per backend — but the method *set* is the shared `ListMethod`/`MapMethod` enum in `lang-stdlib`, so each backend's `match` is exhaustive: a method one backend offers, the other must handle or fail to compile (the differential's static guard). `contains` uses each backend's structural equality (`==`/`values_equal`); `join` uses each value's `display` (so it works on any element type, identically); map `keys`/`values` are key-sorted by the `BTreeMap` both backends use. Misuse routes through the shared `lang-stdlib` error builders (`arity_error`/`type_error`) → `E0007`, so diagnostics match. VM list-building retains each element it moves into a new list (refcount-correct, miri-checked); `lang-value` gained `map_keys`. - [x] **`Set` type.** A third heap value type in both backends (the tree-walker's `Value::Set(Rc<Vec<Value>>)` and the VM's `Payload::Set(Vec<Value>)`), stored in **canonical form** — sorted and de-duplicated — so iteration, display, and equality are deterministic and identical across backends *by construction*. ## M1.10.3 — Ring 2 modules

The user chose the **harness-sandbox** approach for determinism-incompatible Ring 2 (real file IO, wall-clock time): the conformance harness will provide a per-case temp directory and an injected seed/clock so *both* backends produce identical results and stay inside the differential (rather than carving an oracle-exempt hole or deferring IO/time to M2). Differential-safe modules (`json` parse/emit, scalar `math`, seeded `random`) come first; the sandbox lands with file IO + monotonic time.

## M1.10.3 — in progress (Ring 2 modules)

**Access mechanism (decided with the user):** Ring 2 native modules are imported with `use std.{json}` (not ambient prelude names), then called `json.parse(...)`. The deciding factor was **tree-shaking**: with explicit `use`, the import graph *is* the liveness graph, so an unused module drops structurally — matching the project's "smallest binary by default" priority. (Ring 1 stays ambient — you don't import the ability to call `.map()` on a list.)

- [x] **`json` module.** `use std.{json}` binds `json` to a native-module value in both backends — the tree-walker's `Value::NativeModule`, the VM's `Const::NativeModule` loaded + `StoreGlobal`'d at the `use` site (no compiler/loader change beyond recognizing the `std` namespace; the loader already leaves an unresolved `use` in place, and the runtime binds it). `json.parse`/`json.stringify` dispatch through the existing `call_method`/`Op::CallMethod` path. Parsing goes through the shared `lang-stdlib::json` parser (via `serde_json`) producing a backend-agnostic `Json` tree each backend lifts into its values (`null`→unit, object→sorted-key map); stringifying reuses each backend's structural `to_json`. Misuse: invalid JSON → `E0007`, an unknown module function → `E0005` (shared error builders + the new `ErrorKind::UnknownName`). With `${...}` interpolation now in place, JSON literals in source need no brace-escaping. Conformance `std/json.lang` (parse/stringify round-trip, nested object indexing, `null`) + negatives `std/json_parse_error.lang` (E0007) and `std/json_unknown_function.lang` (E0005). Suite **83 passed**; differential **75 matched / 0 skipped / 100% / zero divergence**.
- [x] **`math` module.** `use std.{math}` binds the native-module value; `math.sqrt(2)`, `math.pow(2, 10)`, `math.abs(-7)`, `math.floor/ceil/round`, `math.min/max`, `math.pi()`/`math.e()`. Every function is a **pure** mapping over numeric arguments, so its semantics live once in `lang-stdlib::math` (`call(func, &[Arg]) -> Dispatch`) and both backends are reduced to project-args / lift-`Output` glue — bit-identical by construction. Result typing is per-function: `sqrt`/`pow`/constants → float; `floor`/`ceil`/`round` → **int** (you floor to get an index); `abs`/`min`/`max` **preserve** the argument kind (int in → int out; a mixed `min`/`max` pair promotes to float, as arithmetic coerces). A non-number argument is the shared `type_error` → `E0007`; an unknown function is `no_function_error` → `E0005`. Required a new `Output::Float` variant (lifted in both backends). Conformance `std/math.lang` + negative `std/math_type_error.lang` (E0007).
- [x] **`random` module.** `use std.{random}` binds the native-module value; `random.seed(n)`, `random.int(lo, hi)` (inclusive), `random.float()` (`[0, 1)`). Determinism is load-bearing, so the generator is a **pure stepper** in `lang-stdlib::random` (SplitMix64): given the 64-bit state it returns `(next_state, output)` with no hidden entropy. Each backend holds the state in a single `rng: u64` field, threaded through the shared stepper, so a given seed yields the **identical stream** in both runtimes — by construction, not by test. The state defaults to a fixed `DEFAULT_SEED` so even un-seeded use is reproducible and backend-identical; `seed(n)` makes the stream a pure function of `n`. An empty range (`lo > hi`) is the shared `range_error` → `E0007`. Range draws use 128-bit math so the width never overflows. Conformance `std/random.lang` (reproducibility, range bounds, a pinned concrete sequence) + negative `std/random_empty_range.lang` (E0007). Suite **91 passed**; differential **85 matched / 0 skipped / 100% / zero divergence**.

## Notes / traps
- Ring 2 must stay thin (Go-lean), Ring 1 rich (Python-generous) — stdlib breadth is a curation decision; Ring 3 reuses the extension mechanism rather than a separate stdlib-loading path.
