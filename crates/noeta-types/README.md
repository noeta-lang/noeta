# noeta-types

The type lattice: the vocabulary the type checker reasons in.

- **Takes in:** `TypeRef` (the surface type-annotation AST, from `noeta-ast`).
- **Emits:** `Type` — the lattice (`Int`/`Float`/`Bool`/`String`/`Unit`, `List`/`Map`/`Option`/`Result`, `Named`, `Fn`, unions, and the top `Unknown`), plus `Type::from_ref` (the structural desugar, including `?T` → `Option<T>`) and the `is_numeric`/`is_gradual` predicates the checks key off. (The unused Hindley–Milner `Var` slot was removed once the engine settled on bidirectional-with-subtyping rather than HM unification.)

It also owns the **built-in trait registry** (`BuiltinTrait`, `BUILTIN_TRAITS`, `operator_trait`): the fixed set of traits an `impl` block or `@derive(...)` directive may name (`Add`/`Sub`/`Mul`/`Div`/`Concat`, `Equatable`/`Comparable`/`Display`/`Clone`, …), each recording its required method + arity, the infix operator it overloads (if any), whether the compiler carries a **derive recipe** for it (`has_builtin_recipe` — a body it can synthesize from the deriving type's shape), whether its method is `static`, how many type arguments its `impl` takes, and the **conversion relation** it declares if it is one (`ConversionRole` — which end of the pair its type argument names, and therefore which half of the method signature that argument must agree with). One row per trait, spelling only what is unusual about it: a rule that needs a new fact about traits adds a field here and reads it, rather than growing its own test against a trait by name. A trait without one is not thereby underivable: `@derive(Trait, via: <field>)` delegates several of them through a field, and the user-trait/bundle/extension routes never consult this table. This is the single source of truth `noeta-check` validates against, and its operator → method map is lock-stepped to `BinaryOp::overload_method` (the form the backends use) by a unit test so the two cannot drift.

Subtyping lives here too, as one walk: `Type::subtype_with` carries the covariant/contravariant descent, and the questions it cannot answer from the lattice alone go through the `NominalRules` seam — is this name a type of that kind, does it implement that trait, and is it covariant in that type argument. `Type::subtype` passes `NoRegistry` (every answer "no", which is the conservative direction: each rule only ever *admits* a relation) and `noeta-check` passes its registry. One walk with a seam rather than a pre-test at the caller is what makes each rule compose into a nested position — `List<WebRole> <: List<Enum>` and `List<Dog> <: List<dyn Speak>` hold for the same reason the top-level cases do. The walk carries one flag, whether this position admits a widening at all, and the four relations that read a value at something wider than its own type — `T <: dyn`, `Named <: dyn Trait`, `Named <: Kind` and `T <: A | B` — are gated by it together, so a declared type invariant in an argument refuses all four there. Two unions relate by their member sets rather than through the member rule, which is what keeps the relation reflexive where the flag is off.

Pure data, no inference logic — that lives in `noeta-check`. `Unknown` is compatible with everything and is the fallback wherever a precise type is genuinely not yet known (e.g. an erased generic parameter); it is what lets the inferred-static checker tolerate an *interior* inference hole while still requiring signatures at named boundaries. `TypeId` interning is a throughput optimization deferred until a benchmark justifies it; today `Type` is a plain owned tree.

Part of the `noeta` compilation pipeline (see the repository `ARCHITECTURE.md` and `AGENTS.md`).
